# 系统基础地图设计

> 状态：用户已确认产品方向并授权开始下一步；B0–B6已落地用户选择A的Web可拆片段、独立模板、两种创建与共用地图工作台；B7本地逐项审计已完成，验证范围与限制见[交付核对](system-base-map-completion-audit.md)。来源：本轮用户依次确认“两种创建入口共用地图初始化”“内置可编辑元素控件化”“转换一次保存为系统基础数据、管理员可继续维护、脱离内置游戏”及“本期不扩容，后期再增加地图扩展”。本文件是该模块的详细维护源；任务见[实施清单](system-base-map-tasks.md)。
> 以下属于 Web 产品决定及工程设计，不是原版机制认证。旧地图页面全部作废并重新设计；不因此废除已证共同编译能力或允许猜造规则。

## 1. 目标与边界

在管理员组建立名为“基础地图”的模块（繁体界面“基礎地圖”），仅管理员可见：首次把内置地图整理为符合统一设计的可编辑地图，保存为独立系统基础数据。之后所有游戏创建均复制当前生效模板，不再每次转换内置地图，也不持续跟随内置游戏。

共享的是模板，不是所有游戏共用一份可变地图。普通新建与管理员完整复制调用同一个地图初始化方法；后者只是额外填充人物、章节等初始内容，不存在测试专用地图格式、编辑能力或运行加载器。

本期固定384×256格、16px图块及192原据点槽，保持已证道路/战术绑定边界，不实现地图扩边、增减运行槽或任意拓扑。完成可编辑功能并独立于内置游戏后，后期再增加扩展地图能力。本期限制属于运行能力约束，不得把“内置游戏身份”写成数据格式条件；保留显式bounds、稳定身份与支持域校验，未来扩展须另做消费者适配和验证，不以删除尺寸检查代替。

```text
内置地图资料 ──首次受控转换──→ 系统基础地图模板
                                  ↑ 管理员维护
                                  │ 保存并通过模板检验
                                  ↓ 当前生效版本
                  ┌───────────────┴───────────────┐
               普通新建                       管理员完整复制
                  └─────────同一地图初始化─────────┘
                                  ↓
                        游戏自己的地图数据副本
                                  ↓
                     编辑 → 保存copy → 编译 → 同一引擎
```

## 2. 术语与数据归属

- **系统基础地图模板**：独立于任何可编辑游戏的系统内容；“基础地图模板”为同义简称，不能与四层中的“基本地图”混用。
- **地图元素定义**：可复用的内容配方，包含类别、占用格、锚点、明确变体、视觉绑定、地理作用域及受信规则绑定。不是Vue/DOM控件，也不是作者代码。
- **地图元素实例**：某张地图中实际放置的元素，拥有稳定身份、定义引用、位置、层及顺序等属性。
- **地图组合**：作者明确指定的实例成员关系，例如水域组合；不因渲染、邻接或名称自动推断并重写。
- **游戏地图副本**：创建时从模板物化的独立内容，保留模板版本/摘要作为溯源，不在读取或运行时追踪模板最新版。

模板拥有四层地图、元素定义/实例/组合、必要的据点初始化资料和引用映射、资源依赖及受信兼容绑定。不含章节势力归属、人物任职、运行队列或玩家存档。创建游戏后，据点基础属性仍由该游戏的据点主表拥有，地图放置仅引用该表；不得形成另一份可独立修改的名称/类型/坐标权威。具体坐标写入入口须与据点合同统一。

地图来源与人物/章节来源分别记录：模板脱离内置游戏后，完整复制也不能用一个旧builtin来源标签冒充整个游戏的唯一来源。源标签不是第二份live数据。

## 3. “可编辑转换”的完成标准

转换不是复制图片，也不是把整张旧图包装成背景，更不能仅以256种裸图块和数万个单格实例宣称完成。

1. 建立全图元素清单，覆盖基础地形、山脉/草地/田地/长城等装饰、水域、道路和据点；逐类明确创作粒度、选择/移动/删除/组合行为及当前支持限制。
2. 每个实际格与对象均可追溯到定义、实例或明确的基础格；原子图块可以作为配方构件及明确合理的单格元素，但不能替代所有有意义的组合。
3. 多格元素保存完整footprint/anchor、成员与顺序；同一可复用元素可有多个独立实例，不能用巨大不可拆对象掩盖未完成转换。
4. 原资料未保存的下层明确unknown；移除覆盖物须由作者明确补底，不能从颜色猜原历史或统一填草地。未暴露的unknown不要求伪造，规则输出是否完整由共同编译判定。
5. 四层、地理、视觉、规则输出沿用共同地图合同；水域类别/组合可按明确的Web创作标注整理，不宣称原DOS存在同名对象。改变规则的配方必须有原始证据。
6. 模板中的道路是拓扑与视觉的共同记录，据点引用对应主表和原槽绑定；不把道路贴图当通路，不把新增外观当新增可运行据点。
7. 无编辑转换必须对照原始/已登记基准核规则地形、道路有序数据、辅助资产、据点槽/坐标及战术绑定；视觉和小地图按已批准显示合同验证。
8. 必须用生成模板创建真实隔离游戏副本，完成实际编辑、保存、重读、编译及同加载器运行。只做离线图像或合成DTO测试不算完成。

元素粒度按用户选择A落为Web可拆片段，详细策略/统计/样本见[B0盘点§4.3](system-base-map-inventory.md#43-已批准a的初始web分片合同r8r9)。四连通组按固定16×16格网及格内连通拆成≤256格的可复用片段；不是原版语义对象恢复，不能据图样标签推规则。原子底料保留用于拆分/笔刷，unknown不自动补底；据点跨层外观由作者显式选取，不按5×5或最近距离推断隶属。

## 4. 一次转换与后续维护

首次转换从明确登记且可复核的内置资料生成模板候选，保留来源、映射和差异报告，不写内置原件。完成转换、检查和保存后，后续地图实例化只使用已保存模板，不再执行内置→Web分片转换。创建的历史profile/人物来源验证仍读取登记资料，但不会将其地图覆盖生效模板（§7.3）。

管理员随后直接编辑模板。再次进入模块不得自动重新导入或覆盖已保存编辑；本期不增加自动同步内置、重置所有游戏或批量迁移旧副本功能。

模板保存成功即成为后续创建使用的数据，前提是通过模板自身的完整检查。无效保存不替换现有生效版本，保留界面未保存输入并显示具体错误。若实现中需要跨会话保存未完成模板，须另定义与生效版本分开的编辑态；本期不默认增加多版本管理、审批或回滚产品功能。

保存内部保留准确版本/摘要以绑定创建快照，这不等于开放版本历史页面。并发保存与创建须保证一次创建使用同一份完整模板，不混读新旧定义或资源。

## 5. 创建游戏合同

拟定共用职责“从生效基础地图初始化游戏地图”，具体函数/API名称在实现时按现有架构确定，不维护两套转换算法。

- 普通新建与管理员完整复制都自动捕获同一生效模板；用户不需要选择模板。
- 物化独立地图、定义、组合及必要据点主表初值；内部引用一致重映射，保留原运行槽绑定。局部ID可按游戏命名空间隔离，不要求无意义地重写受信原槽号。
- 完整复制再填充人物、章节和归属；章节对据点的引用须与模板映射匹配，禁止通过复制旧地图覆盖模板结果。匹配失败应有明确错误，不静默丢首都/归属或补规则。
- 创建目标和地图初始化作为同一创建成功边界；失败不留下可见空地图游戏。沿用现有认证、所有权、来源校验及重试合同。
- 模板未建立/不可用时明确拒绝创建，不静默回退到旧内置地图复制路径。
- 修改模板只影响后续创建，不改已有游戏、内置游戏、正式快照或玩家存档；不自动迁移既有copy/publish/formal。
- 不可变图像可共用，但定义/组合/可变数据属于目标游戏；不得依赖模板可变对象的持续存在。

## 6. 管理界面与游戏界面

在现有“管理员”分组新增“基础地图”入口（繁体显示“管理員／基礎地圖”），不受顶部当前游戏选择影响；普通用户不可见且服务端拒绝其读写管理接口。普通创建接口只获取初始化后的游戏数据。

模块应提供：首次转换状态与结果、地图画布、四层控制、可视元素库、选中元素/组合属性、小地图预览、检验问题定位、保存/取消和未保存离开提示。现行布局见§7.5：宽屏为画布、属性、分页资源区，窄屏将资源区移至下方内部滚动，不照搬旧面板。界面使用Element Plus默认主题/组件/size，地图内容画布不变成庞大响应式游戏状态树。

系统模板与游戏地图共用编辑/校验核心，区别仅是权限、读写目标与保存检查范围。游戏级地图页面随后重设计，不复制一套实现；系统模板必须满足新游戏初始化完整性，游戏copy保存继续遵守模块保存与发布全量检验分离。

### 7.2 候选模板合同（已实现）

`server/systembasemap.js` 定义 `system-base-map-1`，显式支持域 `ki-fixed-map-384x256-192-1`，不以游戏ID/builtin身份判支持域。根为 `schema/supportProfile/provenance/content`；当前摘要由完整JSON规范化计算，不保存自引用摘要字段。系统存储的生效版本/事务边界见§7.4。

- `provenance`：首次转换的 `sourceRevision/sourceDigest/policy`。编辑后保留初次来源，当前内容摘要另算，不把初次源摘要伪装为编辑后地图摘要。
- `content`：且仅含 `map/componentDefinitions/cities/compatibilityAssets/editorAssets/selectionGroups`。无游戏ID、人物、章节或运行状态。城市基础初值齐全，固定192槽；游戏创建后成为该游戏自己的主表。
- 四层地图/配方沿用共同合同。非水多格实例携带 `importRef.sourceMembers` 逐格溯源，`unknownUnderlays.coveringInstanceId` 指向物化后的覆盖实例，不恢复未知底图；原子定义保留供拆分/笔刷使用。
- `selectionGroups` 成员为 `{layer,id}`，支持decorations/roads/placements实体引用，成员必须存在且同组不重复；选取关系不增加移动/删除权限。水域显示仍由既存 `map.waterGroups` 的memberIds/baseCells拥有，不用普通选择组覆盖水系语义。
- 原定义/片段定义在模板中物化；素材相同者共享定义，实例独立。游戏复制时内部ID是游戏作用域内身份，可保持局部ID和原运行槽，所有可变结构必须按JSON值复制；不得保留指向系统模板对象的引用。创建来源合同/地图与人物来源分离已接线（§7.3），旧profile不接受这个候选作为旧冻结源。
- `editorAssets` 为不可变图集/参考原图描述符。地图渲染应由当前map+atlas组成，`seasons`原图仅用于保真对照，不能冒充编辑后的地图。结构校验检查描述符；首次转换由38资源SHA验证保证真实字节，保存服务须绑定已信任资源，不能仅靠描述符SHA字符串认为资源存在。

`validateSystemBaseMap` 使用内部、无章节的共同编译投影检查固定槽/节点扫描、道路绑定/辅助数据、unknown、配方和边界；额外检查据点初值、选择引用及资源描述符。这不是玩家游戏或发布票，也没有扩展旧FixedCopyProfile的来源白名单。错误保留共同compiler的明确异常；B3服务需映射为API诊断、保留现生效内容。

`tools/convert_system_base_map.mjs <registered-revision> <new-output-directory>` 显式绑定登记源，拒绝覆盖现有目录；输出template/mapping/receipt三份JSON。内部复用full纯数据投影仅提取主表初值与认证road slots，不将人物章节写入模板。无编辑候选与原源逐字段比较共同编译全部输出，并再次带真实20章编译核对邻接/坐标；实际落地的资源/生效存储不是该离线转换工具的副作用。

### 7.3 单快照实例化与历史来源边界

系统存储对创建提供 `{version,digest,template}` 单快照：version为正安全整数，digest必须等于template完整规范化摘要。`instantiateSystemBaseMap(game,snapshot,sha)` 不自行重读“当前模板”，缺快照/错摘要立即拒绝。完整复制/普通新建均已通过 `AdminFullCopy` 接此函数。每次实际执行在首个await前捕获一次独立快照；执行期间不再追随最新模板。失败执行不安装copy，后续新执行可采用届时模板；已提交操作的重试直接返回原收据，不重新实例化。

- 输出深复制全部可变数据，以模板替换map、componentDefinitions、cities、compatibilityAssets、selectionGroups，资源描述符存入 `mapEditorAssets`；不可变图集字节仍共享可信资源地址，不复制到某款游戏可删除前缀。
