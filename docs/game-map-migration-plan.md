## 1. 两项任务的关系

设计顺序与实施顺序分开：

```text
任务一：确定编辑器方案（含统一地图源、编译、加载与编辑规则）
  ↓ 方案确认，记录准确合同版本
任务二：按该方案改造当前游戏地图 → 验证 → 确认无问题
  ↓
后续：依照经过验证的方案实施编辑器
```

- 原游戏是统一地图设计的第一个真实使用者。Q50后用户更正：编辑器不得直接修改原件，必须先复制为独立新游戏；第一个可编辑实例改为原游戏测试副本，详见任务一第3节。
- 编辑器界面可以尚未建成，任务二用受控迁移工具和隔离内容样本验证同一结构的可编辑性；不能因为原件只读就让内置图继续走另一种源格式。任务二验证不代替后续编辑器实际复制新游戏、编辑副本、保存、校验编译及同引擎加载验收；Q67新增的游戏列表“測試運行”列、独立窗口、草稿访问授权与正式存档隔离属于后续编辑器验收，不纳入本任务的互联网功能范围。
- 原游戏的受控工程迁移与编辑器修改是两个边界：本任务仍按已确认方案改造当前游戏并保留原资料／基准，但不授予任何账户通过编辑器写入内置原件的权限。
- 迁移发现方案不能表达原地图时，回流任务一修订并确认相关合同，再更新迁移与测试；不在任务二增加绕过统一校验的内置专用规则。
- 设计编写轮只调整设计。后续实施中的局部证据缺口仅暂停依赖它的部分，独立已授权工作继续；未满足全部门槛不得宣布任务二完成。

## 2. 目标与明确不包含

任务二必须交付：

1. 当前游戏实际使用自动生成的小地图，不再依赖手工渐变中间图。
2. 当前地图与编辑器地图采用同一创作构成、编译／校验合同及运行加载入口。
3. 在已支持容量内，以内置地图和隔离修改样本验证同一引擎加载与规则安全。
4. 保存原始证据、迁移差异和可复核验证结果，为编辑器实现提供已验证基础。

不包含互联网账户／权限服务、完整编辑器界面、玩家游戏目录及通知、完整人物／章节CRUD、生产发布或任意规模扩边。容量风险需先审计，实际扩容仍按任务一后续切片办理。统一数据结构不能自动解除现行384×256地图、192据点及其它固定槽／地址限制。

### M0：核对已确认设计与迁移基准

- 输入是任务一已经确认的地图合同，不在此另设计一个只服务原图的结构。逐项映射地图范围／坐标、地形与水系、组件定义／放置／覆盖、据点／道路、资源身份和修订。
- 核对规则字段的原始来源、派生输出及支持／拒绝域。区分组件外观、规则地形和小地图显示分类；不能从颜色猜通行能力，也不能因为小地图省略山脉而删除其规则地形。按任务一Q64记录明确的河流／湖泊／海洋类别及原图导入依据，不将旧脚本的边缘连通启发式直接充当分类证据；原资料不足处列明缺口。
- 按任务一Q58及第4.4.4节核对基本地图、地图装饰、道路、据点四个独立编辑层及其自下而上顺序，基本地图与装饰不合并；逐项核对规则输入映射。不把旧编译器对下层地形的检查直接转成编辑放置禁令，也不把“装饰层”当作无规则作用。
- 核查组件移除后的底层恢复资料；不能恢复的部分列明证据缺口，不为原件补造规则数据。Q57已确认副本删除未知底层组件时由作者明确选择替换地形；恢复不得回滚其它后续修改，关联检查不能仅因道路／据点下层地形种类而拒绝。
- 固定迁移前输入／输出和已覆盖规则基准，保留原始资源；在新目录试编译比较，不覆盖原DOS资料或旧验证证据。
- 生成256原图块到组件／视觉／地理／规则recipe的映射清单，记录拆组依据、已知覆盖和未知底层；水系展示标注可以作为Web视觉资料审核，不能把人工海／河分类当原通行证据。未解释的图块保持原子可编辑记录及原字节，不整图封装或猜填。
- 原192节点、254边的边内点流只读检查已取得跨边共享点／线段／单位斜X均0，来源及算法见排查§3.1；实施仍需补节点中心到端口、组件footprint与新编辑占用规则。若发现特殊端口相接或原图几何与产品约束冲突，核对原资源及“据点连接区域”定义并回流合同，禁止给内置身份增加跳过校验开关。
- 列明内容／世界身份、资源缓存键与存档准入的影响，具体差异矩阵见本节后文；不能为了让测试通过刷新旧预期、伪标旧修订或清库。

### M1：自动小地图（首个可见交付）

本轮用户已认可水域显示类别，并在m1668认可主河摘要、同色道路/水系及渐变点阵新候选（M-06）；批准的精确图像/来源/范围已记录，未扩展为DOS机制认证。最新隔离revision/实测/同尺寸对照由[水域审核页](map-water-display-review.md)维护，不因类别认可就代签新美术；后续组合编辑器UI不在任务二范围。

- 依据任务一的小地图显示合同，自动生成地理底图、纹理渐变及道路水系摘要，彻底移除手工修图这一必需步骤。Q65的目标是尽可能接近原游戏配色、渐变与表面随机感纹理，不是平涂替代；对照原游戏视觉参考验收，不将用户的外观描述当作原版纹理生成算法或RNG消费的证明。
- 自动生成允许输出并缓存图片，不要求每帧重算。相同输入、生成参数和生成器版本应可复现；不使用游戏规则RNG，不修改Scenario。
- 当前游戏实际接入结果，底图、动态据点／军团路线／战斗标记、视口框与点击定位共享范围和坐标变换。保留现行UI输入优先级、地图锁、hold与导航边界。
- 按任务一Q53／Q54保持完整海陆/河湖/静态路网资料；本轮用户补充要求只在小地图按实际组合的内容开关显示摘要（不是每个细支流都画），完整地理和规则不删，静态道路独立保留。组合字段/叠层/默认/校验唯一维护于工程合同§2.2.2，主河带是Web显示候选，不认证原具名河流对象。动态军团路线不能替代道路；纹理不遮断线条。地图等比例完整显示，留边不导航，实际地图显示矩形用于覆盖层和点击映射。
- 按任务一Q55，必要时将地图显示区域宽高各放大约20%，外框及底部势力名牌相应调整；空间不足则回退较小尺寸，不强制放大，也不能只拉伸旧图片。验证外框、名牌、相邻UI及绘制／命中范围，覆盖放大与回退布局；纹理风格按Q65的已确认目标，具体参数经实际对照收敛，不在本任务另换风格。
- 若需要分步导入，原资料适配只负责输出统一结构；后续M2继续使用同一小地图生成器，不留下“原图手工图／新图自动图”或两套生成算法。
- 按任务一Q62验证田野遮挡河流仍保留水系地理资料，小地图继续显示河流；明确编辑／删除河流组件后再按当前水系更新。按Q66增加河流／湖泊／海洋相交样本，验证重叠区域取最上方水域类别，调序后摘要相应变化，删除上方后显露当前下方水域；叠放非水域装饰不改变此选择，各组件自身类别与道路类型不被改写。不得以大地图截图最上方颜色替代地理资料，此展示验收不证明规则通行映射已闭合。
- 小地图纯生成与坐标测试可以覆盖不同比例；这不是批准超容量地图进入规则引擎。

### M2：当前地图统一构成迁移

- 将当前地图所需资料纳入任务一统一的可编辑源，保留图块语义、已证规则字段、有序道路数据及来源；不能把完整旧图当不可编辑背景，外包一个新格式就视为完成。
- 由同一编译管线生成大地图资源、规则输入及自动小地图；同一加载引擎消费编译结果，不临时解释两套作者格式。
- 当前章节、季节与战术关联保持有效。底图、道路、据点及动态覆盖所用资源必须来自同一修订；旧异步结果不得写回新世界。
- 原始DOS资源保持只读，迁移先在隔离输出中比较验证；当前Web游戏接入受控迁移结果不等于开放编辑器原件写入。后续编辑器测试仅修改独立副本，管理员也不能绕过原件保护。

### M3：隔离编辑样本与同引擎验证

- 从统一源建立独立样本，在已证支持域内修改、重新编译并加载，证明结构不只是重新包装内置地图。
- 不依赖尚未建设的账户、发布服务或完整编辑UI；受控测试资料即可验证。复制与修改不得反改内置源或其它世界缓存。按任务一Q63保留明确来源修订，隔离样本固定复制时内容；在测试来源的另一修订上模拟更新，确认样本不会追踪最新来源而改变，不修改真实原件来执行此项验证。
- 内置图和样本使用同一校验器、编译器、加载入口与规则，不以游戏身份跳过缺失字段、坏引用、未知规则能力或容量错误。
- 在已完成规则映射的支持域内验证叠层与删除恢复：组件网格落点正确，上层道路／据点不因下方地形种类被禁止；保留道路连接及引用校验。下层已知时正确显露，未知时不猜填，修改副本不破坏原件或其它组件。未闭合的组合列明缺口，不以仅能绘图作为可运行证明。
- 按任务一Q61构造装饰同层叠放样本，验证放置顺序、同层调序与删除上方后显露下方，保留下方组件及其它后续修改；不得将同层许可扩展成道路交叉豁免。若测试样本含编辑显隐／锁定状态，按Q60验证其不改变正式编译内容。完整选层、防误选与锁定UI验收属于后续编辑器，不扩大本任务为编辑器建设。
- 先获得所有适用门槛证据，再确认任务二完成并进入编辑器实现；M1成功不等于M2、M3成功。至少一个样本必须真正修改已支持的地图组件内容并改变相应派生产物，不能仅改包名／ID或重编未变原图冒充编辑。

### 身份、缓存与存档切换

- 内置gameId／packId保持`wolong-builtin`，world.id保持`mmap-original`，章节ID与运行索引不改；新的源／运行格式及资产清单产生新的contentRevision／worldRevision。不能为了旧档通过伪装成原revision `1`。
- 迁移后的静态内置manifest是受控工程交付，不是管理员通过编辑器发布原件。正式游戏版本由受控清单明确登记，旧catalog revision `1`不自动等于游戏版本1.0；若引入首个显示版本，必须附带清晰的旧身份区分，不能给旧档补标签。
- 已运行旧页面不热换场景，保留自己的修订；受控发布资产须确保旧页面延迟资源仍可取。任务二虽不实现线上发布服务，也须验证新旧输出目录可并存，不能用清空旧资产完成切换。
- 新页面只装配新manifest；缓存按世界／内容修订及hash隔离，失败Promise可重试，普通刷新无需手动清缓存。若使用service worker，需核实际缓存路径与更新时序，不假设仓库已有它。
- 测试只创建内存／隔离profile档。迁移前模拟档若身份不同应明确拒载、保持原样，不能加载后临时替换世界。身份缺失或旧格式不按“版本不符”自动删除；后续多游戏版本确认清理才按工程合同第8.2节执行。
- 不以对局JSON往返成功证明旧档兼容；分别记录“本次新格式自往返”“原身份拒绝”“坏能力拒绝”和“原始规则对照”的证据。
