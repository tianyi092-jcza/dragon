# 第二阶段：表现层现代化

用户批准先提交现有成果，再开始本阶段。此前存储/内容扩展的“第二阶段”见[另文](web-refactor-phase2.md)，不与本阶段混淆。

## 原则与边界

还原的是游戏规则，不是DOS渲染技术。继续使用原生ES Modules与Canvas 2D，无框架、构建或运行时依赖。AI、规则时序、天气作用位置与范围、随机数消费、消息顺序、六队结果及存档不因表现升级而改变。

规则Clock和表现时间不互相替代：规则层产生离散权威状态；表现层只读采样，在自己的时间轴上绘制。表现状态不进入Scenario/IndexedDB，也不反向驱动规则。军团位置仍受规则步点/周期约束，不可为了流畅提前到城。

## 本批完成：独立表现时钟与云雨

- `render/presentationclock.js`：接收RAF时间，首次/恢复帧零增量，可见慢帧最多推进100ms而非整帧丢弃，避免战略计算持续超过100ms时动画永久停住；超额不积债，后台显式pause，恢复首帧不补后台时间。没有速度档、日期、RNG或存档依赖。
- `render/weatherpresentation.js`：每App实例持有16个独立视觉槽，只读`weatherClouds`的存在、active、group、XY及原帧号frame。位置使用120ms时间常数平滑趋向已提交坐标；创建/移除300ms淡入淡出；相邻两次权威位置大于4格的跳变只重新定位，避免回卷云团扫过全地图；不以显示位置的追赶距离判断跳变，也不重置已有云团透明度/动画，防止高速连续移动反复消失。这些参数都是**Web表现选择，不是原版天气公式**。
- **现行外观（用户明确要求恢复原版）**：直接绘制`grf/weather/cloud_frame_0..7.png`原完整云雨帧，禁用图像平滑；包含原云体、雨丝及透明区域，不重新绘制渐变云团或叠加额外雨丝。初始帧号只读自规则对象，随后按独立表现时间每100ms播放原八帧循环（Web表现节拍，不是DOS规则周期）；原生天气规则不推进该frame字段，直接持续读取它会导致静止，故不能将其作为动画时钟。此前深灰/白色渐变方案均已退役；保留平滑位移与淡入淡出，稳定显示时与原PNG逐像素一致。
- 原16×9格显示框与层级保留：灾害之上、UI之下。规则天气位置不变，平滑坐标和消失后的短淡出只代表视觉残影，不能用于命中/伤害/速度判断。
- `main.js`在规则更新之后独立更新表现；`MapView`只绘制已采样的表现状态。反复draw不推进时间、粒子或天气槽。
- **现行暂停政策（用户明确澄清，取代暂停仍播放）**：云雨跟随战略计时。`speed<=0`或任一`hold`（包括鼠标/菜单）时，表现时钟、位置收敛、淡入淡出及雨丝帧全部冻结；计时恢复后继续播放，不补暂停债务。页面隐藏、runtime禁用、离开战略场景或场景过渡时冻结；Scenario身份改变清空旧表现。接战音/动画仍按其既有暂停与五声政策，不在本批合并生命周期。
- 正式进入地图前预载全部八帧原云雨PNG，避免首帧空白；复用既有解码资源及原证像素校验。火灾/暴动暂时仍用原图，未改变它们的规则/像素。

## 验证合同

独立时钟与30/60Hz同时间采样、淡入淡出、回卷、暂停/恢复、Scenario替换、输入不变性用纯内存测试；正式浏览器验证八帧实际绘制与原PNG逐像素一致（含透明区）、重复draw一致、Scenario/RNG未修改、战略暂停下表现状态/时间完全冻结、战略运行且每帧人为增加120ms负载时动画仍推进、八帧资源均就绪，并保留火灾/暴动及TALK71/72回归。完整执行结果与覆盖限制只记录在[journal](checkpoint-journal.md)。这是对已实现Web合同的验证，不宣称美术效果已获用户验收或性能已经提升多少。
