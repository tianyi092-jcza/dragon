# 城池据点（基础资料）与章节属性归属（模型合同）

按用户定义建立：**剧本 = 底层基础资料（全章共享）+ N 个互相独立的章**。章节**引用**基础资料，不复制；
因此「改基础属性」自动传导、「删基础资料」使引用它的章失效。本文是字段归属与校验口径的单一维护源。

## 1. 城池据点等基础资料（游戏级，全章共享，章只引用）

| 类别 | 字段（作者层） | 来源 | 章可修改？ |
|---|---|---|---|
| 地图地形 | `map`（tile、`componentDefinitions`） | 剧本 | 否 |
| 道路 | `map.roads[].fromCityId/toCityId` | 剧本 | 否 |
| 地图放置物 | `map.placements[].cityId` | 剧本 | 否 |
| 据点定义 | `cities[cityId]` = `{cityId, runtimeSlot, x, y, name}` | 剧本 | 仅经 `overrides`（当前关闭） |
| 武将资料 | `generals[generalId]`：姓名、字、头像、能力（siege/field/naval/force/lead/politics）、`talk_idx` 等 | 剧本／固定源 entity-source | 仅经 `overrides` |
| 固定运行槽 | 据点 192 槽、武将 128 槽（`runtimeSlot`/`idx` 锁定） | 剧本 | 否 |

依据：`web/src/content/authoring/cityrecords.js`（定义键白名单 `cityId/runtimeSlot/x/y/name`）、
`gamesource.js:316-332`（192 据点、道路/放置物引用检查）、`generaldefinitions.js`（`generals` 定义 + `captureScope`）。

## 3. 校验规则（发布前试运行的口径）

1. **引用完整性**：章节引用不存在的 `generalId` / `cityId` → 该章失败（`gamesource.js` 定义与引用分离）。
2. **删除即失败**：基础资料被任何章引用时不得删除——`generaldefinitions.js:161-163` 在保存期直接拒绝
   （`general definition is referenced by chapters`）；据点同理由 `captureCityDefinitions` 保证键存在。
3. **改属性不失败**：改基础名称/能力/头像，无 `overrides` 的章自动继承（`inheritance()` 返回
   `inheritedFields`/`overriddenFields`），属正常传导，不产生缺口。
4. **章节内删除**：删势力 / 删据点引用 / 删武将引用 → 该章 `factionId` 或引用悬空 → 按 1 处理。
5. **全章汇总**：单章试运行只覆盖当前章；发布前试运行须遍历 `chapterOrder` 全部章，
   一次列出「哪些章因某基础资料被删除而失效」（防止基础资源地图、据点、武将缺失）。
6. **势力必须有首都（Web 作者层，2026-11 用户口径）**：`createFaction` 只建槽与纳君主，
   首都留空（`+03`＝`FF`／声明值 `null`）。`chapterActiveGaps` 对 `capital` 同时报
   `entity-field`（该字段要求整数）与 `entity-ref`（引用未知）两条缺口，因此**没有首都的势力
   既不能保存也不能试运行**，无需第二套门槛。建势力时 `n_cities`／`n_generals` 按本章现况
   派生（新势力 0 据点、1 武将；内政官不计入 `n_generals`），其余未证实位元组沿用固定源同槽。
   - **未实施**：`首都必须属本势力`（计划第 6 步）。原版数据有 8 个内置势力首都所在据点的
     `+01` 并不等于该势力，`gamesource.js` 的 `setFactionCapital` 注释已按原始证据保留该反例，
     所以这条只能作为**已标记的 Web 产品决定**落地，不能当成原版规则；需先定「内置章豁免」口径。
7. **武将登场／身份（Web 作者层写入器，2026-11）**：`setGeneralActive` 同步写 `attr` bit7（登场，
   见 §2）与作者层视图 `active`，`attr` 其余位（含 bit6 君主）原样保留；`setGeneralStatus` 写
   `G+17`，只接受 `0–4`（待命／军团长／内政官／外交官／被俘）。`0–4` 与 `G127 保留槽`是**作者
   输入限制**，不是从 KI 反推的值域。两者都不是新保存门：`chapterActiveGaps` 不因登场或身份
   产生缺口，身份也不改变所屬、任職或任何计数（要改所屬走 `setChapterGeneralFaction`，任職中
   的武将会被拒）。回放层面 `general-active`／`general-status` 已加入两条 profile 的章節属性
   白名单；其回退**先验后还原**（候选值必须整体等于「建立时快照＋同一 writer」或整体等于建立
   时快照，否则拒绝），避免盲还原吸收未申报改动。
   - **已知共通限制（未改）**：`general-faction`／`set-monarch`／`set-capital` 等单栏 op 的回退
     仍是盲还原，「宣告了但没生效」与「未改动」不可区分；不要拿它们当覆盖证据。
   - **未实施**：按勾选顺序占槽（计划 §5.2 已拍板的 Web 决定）。当前 `addBlankChapter` 的 128
     槽是固定源第 1 章骨架（未登场），勾选只切换登场／身份／所属，**不写姓名、头像或能力**；
     真要做「从游戏级武將庫按勾选顺序落槽」需先决定未勾选槽是否允许空姓名（现 `chapterSaveGaps`
     要求 128 槽姓名非空）。

## 5. 已知不一致（待裁决，勿默认为已实现）

1. **据点势力归属未开放**：作者层 `captureChapterCities` 强制 `factionId === null` 且 `overrides` 必须为空
   （`cityrecords.js:29-36`），而原生状态层 `cities[].faction` 存在并被 AI/规则使用。
   → 「据点的势力所属是章节定义的」在数据层成立，在编辑入口尚未开放。
2. **两层表示并存**：作者层用 id 键（`cities[cityId]`、`people[generalId]`），原生状态用定长数组
   （`cities[192]`、`generals[128]`、`factions[]`）。两者之间的唯一转换点尚未在文档中声明，
   与「契约方言统一」属同一件事。
   B5（2026-11）已让作者层对**游戏自有来源**（`builtin-template` 与 `builtin-copy`）可读写：
   `game.generals` 是默认空的武將庫、`chapter.people` 是章節引用，命令只改这两个根；库 → 原生
   128 槽的 materialize **仍未做、未裁決**，因此导入不等于可試玩（见 `checkpoint-journal.md`
   「B5 武將庫」節）。舊槽位字典不是庫，读写都 fail-closed。

## 6. 玩家端存档校验（用户决定）

覆盖发布后：旧版本在玩家端不可选；加载存档时校验 ①**游戏是否仍存在** ②版本标识。
`web/src/player/playersaves.js:15,20` 把存档绑定到
`releaseId / releaseOrdinal / manifestDigest / sourceDigest`，不符时抛 `TypeError`；不需要新版本机制。

B7（2026-11）已实现面向玩家的结果，两者口径不同：

| 情况 | 判定 | 面向玩家 |
|---|---|---|
| 游戏已不存在 | 仅 reader 明确 `410 GAME_DELETED` | 「該遊戲已被刪除，存檔不可用，是否刪除？」→ **确认**才逐槽 `compareDelete`（无法核对的槽保留并按数报告），**取消／右键**保留 |
| 版本不符 | 既有身份字段比对 | 旧版存档不能载入并**自动清除**（已批准政策，不逐档确认）；无法判定为旧版的行保留且不载入 |

维护源：`web/src/player/playerdeletedgame.js`；接线在 `playerpublic.js`（载入入口）与 `playerrestore.js`（读档选择器）。
细节与证据见 [R2 接线 §2.73](r2-player-connection.md) 与 `checkpoint-journal.md`「B7」節。

## 7. 建立章节（用户设计 2026-11，待实现）

### 7.1 前置门控
创建游戏后先完成三件游戏级资料：**管理地图 → 管理据点 → 管理武将**；建章之后才可编辑章节三面。

### 7.2 「新增章節」对话框

| 字段 | 控件 | 规则 |
|---|---|---|
| 章節序號 | 下拉 1–10，已占用项禁用 | 显示「第一章」…「第十章」；作者最多建 10 章（**Web 产品决定，非原版机制**：原版 `SINARIO.DAT` 每剧本 4 章、内置共 20 章）；序号保存后不可改、删除后空位不补 |
| 章節標題 | 文本框 | 必填，≤16 个 Unicode 码点（trim＋NFC，复用游戏名规则）；列表显示「第三章 · 标题」 |
| 紀元 | 下拉 公元前／公元 | 作者层纪年标签，**不把年份取负** |
| 開始日期 | 年（纯数字 ≤4 位）／月 1–12／日 1–31 | 只做输入范围，**不做日历合法性校验**（未见原版证据） |

保存 → 章节列表出现该章。**第一章**额外带入章节态：据点所属势力、首都标记、势力集合、武将出场与身份；内政官／外交官按 §8 裁决一律初始为空。

### 7.3 章节三面的顺序

1. **势力＝勾选本章君主**（武将 `attr` bit6）→ 生成势力槽；**定义势力时必须指定首都**，首都所属据点随之归属该势力（用户口径：君主即势力，必须有据点，否则所属武将没有出场落脚点；只有武将可以随时登场加入）。
2. 军师／外交官／内政官：章节定义可预先指定以便测试（开局为空、运行后委派是原版行为）。
3. **据点章节属性**：所属势力／中立／首都。
4. **武将章节属性**：勾选本章出场武将（来源＝游戏级武將庫，仅基础信息）＋身份（`general+0x17`：0 待命／1 军团长／2 内政官／3 外交官／4 被俘）＋所属势力（`+0x1C`，`FF`＝自由）。**职务不属于武将**：军团长在军团 `+2`，主将／先锋／左翼／右翼／左备／右备在军团 `+0x28..0x3F`。

### 7.4 校验
- 定义势力时必须给首都（有首都 ⇒ 至少一个据点）。
- 试运行／上架：每势力至少 1 据点；恰 1 个自动成首都；多个必须且只能选 1 个首都；0 个不通过。
- **内置 20 章不套此校验**（改版章节有 8 例违规，见 §8）。

### 7.5 生命周期与已定口径（控制方 2026-11 拍板）

| 事项 | 定论 |
|---|---|
| 空白章的「当前生产力／城兵」初值 | 取固定源第 1 章同槽值，**最终口径**（唯一有原证来源的填法，不是新规则） |
| 128 武将槽分配 | **按作者勾选顺序**占用槽位，不固定槽复用；为后续「武将数量可动态定义」扩展让路 |
| 地图/基础资料变更与已建章 | **建章时一次性** materialize 章节态；之后改地图或基础资料**不自动回写**已建章节 |
| 第一章的特殊性 | 只在于创建时**顺带带入游戏基础数据**（章节态快照）。带入完成即完成目标，此后第一章与其它章**完全等价** |
| 删除章节 | 任何章（含第一章）都可删，**删除章节永不删除基础数据** |
| 基础数据生命周期 | **归游戏**：由第一章产生，由**删除游戏**删除。全部章节删光后基础数据仍然存在（游戏仍是草稿，不可试运行／上架） |
| 重建第一章 | 允许；机制与其它新章相同（照样按当次基础数据 materialize 章节态），不会重复生成或删除基础数据 |

> 换言之：**章节态由建章动作产生，游戏基础数据由游戏存续**。两者生命周期不同，任何实现不得把「删第一章」实现成「删基础数据」。
